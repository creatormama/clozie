## THE BUG (as reported)

After the app has been inactive / backgrounded for a long time, the user reopens Clozie. The Closet screen itself IS visible (the screen renders, item cards/layout appear), but the clothing item IMAGES do not load — they stay blank/empty. Force-quitting the app and relaunching fixes it every time.

---

## ROOT-CAUSE DIAGNOSIS (verified against code)

**The images are private Supabase Storage SIGNED URLs with a 1-hour expiry, minted once on Closet mount and never regenerated on foreground return.**

Mechanism, step by step:

1. Images are private Supabase Storage signed URLs (not public URLs). Generated by `getSignedPhotoUrl` → `createSignedUrl(...)` in `src/lib/wardrobeItems.js:56-63`.
2. **TTL = 3600 seconds = exactly 1 hour** → `src/lib/wardrobeItems.js:8` (`const SIGNED_URL_TTL_SECONDS = 3600;`).
3. On the Closet, they are minted **once**, inside the `loadItems` function in a `useEffect` with an **empty dependency array `[]`** → `App.js:7789-7829`. It fetches item rows, then `Promise.all` mints a signed URL per photo (`App.js:7799`) and stores it as `photoUri` in the `wardrobeItems` state (`App.js:7806`).
4. The grid renders that stored URL directly: `<Image source={{ uri: item.photoUri }}>` at `App.js:2138-2142` — **no `onError` handler, no retry, no refresh.** If the URL is dead, the image is silently blank.
5. React Native keeps `MainAppScreen` **mounted in memory while backgrounded**, so `loadItems` (empty dep array) does **not** re-run on return. The metadata in state is intact but every `photoUri` is now an **expired** URL.
6. Result: layout renders (metadata in memory), images blank (expired signed URLs).
7. Force-quit → app restarts → `MainAppScreen` remounts → `loadItems` re-runs → fresh signed URLs → images work. Matches the "relaunch always fixes it" symptom exactly.

**Why it only happens after a LONG background:** matches the 1-hour TTL. Short backgrounds keep the URLs valid.

**Competing hypothesis considered and REJECTED — expired auth token:**
- There IS an AppState listener → `App.js:8356-8365` — but it does only one thing: `supabase.auth.startAutoRefresh()` on `active`, `stopAutoRefresh()` on background. It does NOT reload the wardrobe or refresh any image URL.
- Even if the auth token refreshes perfectly, that does nothing for the signed URLs. A signed URL is a standalone, time-stamped link — once its hour is up, it is dead regardless of session health.
- The token is not the problem. The URL expiry is.

**No other relevant paths:**
- No foreground refetch for the wardrobe. The only AppState handler is the auth one above (`App.js:8356`).
- No realtime/websocket subscription for wardrobe items. The only subscription is `onAuthStateChange` (`App.js:7816`), which handles `SIGNED_OUT` only.

**Single most likely root cause (one line):** signed-URL expiry (1h TTL) with no regeneration on return-to-foreground.
Root lines: `wardrobeItems.js:8` (1h TTL) + `App.js:7789` (load-once effect, never re-runs) + `App.js:8356` (foreground handler that refreshes auth but not images).

## OPTIONS CONSIDERED (A / B / C / D)

| # | Approach | Size | Risk | Notes |
|---|----------|------|------|-------|
| A | On AppState→`active`, **re-mint signed URLs for items already in state** (map over existing `wardrobeItems`, no DB refetch, no hard replace) | Medium | LOW | The real fix. Sidesteps the documented `loadItems` merge-race because it never re-fetches rows or replaces the array wholesale. **CHOSEN.** |
| B | Add `onError` to the grid `<Image>` so a dead URL self-heals by re-minting just that one item's URL | Medium | LOW–MED | Surgical/self-healing, but touches render + needs a per-item refresh path. |
| C | Just **increase the TTL** (e.g. 24h / 7 days) — one constant | Small | LOW | Mitigation, not a fix. A longer-than-TTL background still breaks. Cheapest possible. |
| D | Make the bucket public (`getPublicUrl`, no expiry) | Small | **HIGH — REJECTED** | `wardrobe-photos` is a private, per-user RLS bucket. Public = privacy regression. Do NOT do this. |

**Why D was rejected:** `wardrobe-photos` is a private bucket scoped per-user via storage RLS. Switching to public URLs would remove that protection and expose every user's wardrobe photos via un-expiring links — a privacy regression. Not acceptable.

**Decision (not paired with TTL bump):** Ship Option A alone. One change at a time. A resolves the reported symptom. A TTL bump would just be a second variable to reason about; it can be considered as a separate tiny step later if belt-and-suspenders is wanted.

## THE `loadItems` RACE — UNDERSTOOD, AND OPTION A AVOIDS IT

**What the race actually is** (already logged in KNOWN ISSUES):
- `loadItems` ends with `setWardrobeItems(itemsWithUrls)` at `App.js:7806` — a **hard replace** of the whole array.
- `handleAddItem` does an **optimistic prepend** `setItems((prev) => [{...newItem}, ...prev])` at `App.js:1550`.
- If you add an item during the ~200–800ms load window, the later-arriving hard replace at 7806 clobbers the prepend. **That race window exists only during the one-time mount.**

**Option A avoids it for TWO independent reasons:**
1. **Timing:** Option A fires only on foreground-return, gated to >45 min after the last mint. Nowhere near the 200–800ms mount window. The two never overlap.
2. **Mechanism:** Option A uses the **safe functional-map setter** — `setWardrobeItems((prev) => prev.map(patchPhotoUriById))` — the exact pattern already proven safe at `App.js:8139` (`handleMarkItemsWorn`) and `App.js:8192` (`handleClearMemory`). It operates on whatever is currently in state (including any optimistic add) and only swaps `photoUri` by id. It **structurally cannot drop an item**, unlike the hard replace.

The fix would NOT touch line 7806 or the existing load effect's core.

## NO OTHER CLOSET-IMAGE CODE PATH (confirmed)

- **URL creation** happens in exactly THREE places, all confirmed: `getSignedPhotoUrl` at `App.js:1543` (add), `App.js:1626` (edit), `App.js:7799` (initial load). `createSignedUrl` exists in exactly one place: `wardrobeItems.js:60`.
- **Every display site** — grid `App.js:2138`, pin sheet `App.js:2952`, plus mood/hanger/share card — reads `.photoUri` off the same `wardrobeItems` state objects. So a single re-mint of `wardrobeItems` refreshes the closet grid AND the pin sheet in one shot.

## OPTION A — PRECISE SPEC (PLAN ONLY, nothing applied)

**All changes in `App.js`, inside `MainAppScreen`. No changes to `wardrobeItems.js`, no TTL change, no touch to the existing auth AppState listener (`App.js:8356`) or the load effect's core (`App.js:7806`).**

1. **Add one module-level constant** (near other consts):
   `const REMINT_THRESHOLD_MS = 45 * 60 * 1000;` (45 minutes)

2. **Add two refs** next to `wardrobeItemsRef` (declared at `App.js:7773`, kept in sync at `App.js:7786`):
   - `lastMintRef` — timestamp of last successful mint, init `0`.
   - `remintInFlightRef` — boolean guard against overlapping re-mints, init `false`.

3. **Set the timestamp on the existing successful load** — one line added inside `loadItems` right after `setWardrobeItems(itemsWithUrls)` at `App.js:7806`:
   `lastMintRef.current = Date.now();`
   (Optional minor: also set it in add/edit success at `App.js:1550`/`1650` so a fresh add doesn't immediately look "stale".)

4. **Add one NEW `useEffect`** with its own `AppState` listener (separate from the auth one at `App.js:8356` — leave that working code untouched). On `state === 'active'`:
   - If `remintInFlightRef.current` is true → skip.
   - If `Date.now() - lastMintRef.current <= REMINT_THRESHOLD_MS` → skip (cheap short-circuit; a 10-second background does nothing).
   - Otherwise: set guard true; read `wardrobeItemsRef.current`; `Promise.all` re-mint a fresh signed URL per item that has a `photoPath`, **each wrapped in try/catch that falls back to the item's existing `photoUri` on failure — never blanks anything**; then `setWardrobeItems((prev) => prev.map(byId-merge of new photoUri))` (safe functional-map setter, merge by id); set `lastMintRef.current = Date.now()`; clear the guard in a `finally`.
   - Clean up the listener on unmount (`return () => sub.remove();`).

**Re-mint frequency rationale:** gate on **time-since-last-mint (URL age)**, using a `useRef` timestamp. This is cleaner and more correct than tracking background-duration, because URL age is the actual cause. Threshold 45 min = safely under the 1-hour TTL, 15-min margin so we never serve a URL that expires seconds later. A `useRef` (not state) survives across renders while mounted, causes no re-render itself, and reuses infrastructure that already exists (`wardrobeItemsRef` at `App.js:7773`/`7786`, read via `new Map(...)` at `App.js:7919`/`7967`).

**Net change:** ~1 constant, 2 refs, 1 timestamp line, 1 new `useEffect` (~25 lines). Zero deletions. No existing logic modified.

## FINAL RISK LEVEL: GENUINELY LOW

- Uses the already-proven safe functional-map setter → cannot drop items, cannot re-trigger the mount race.
- Additive only — no existing working code (auth listener, load effect, hard-replace) is touched.
- On re-mint network failure, it keeps the old URL → never worse than today.
- Gated → no wasteful churn on short backgrounds.
- Honest nuance (not zero): it introduces a new lifecycle effect that, when it fires, causes one closet re-render as URLs swap. Worst realistic downside is a brief image refresh flicker on return after a long background — cosmetic, and only in exactly the scenario that is currently fully broken. Still LOW, but the flicker possibility is not literally zero.

## TWO HONEST OPEN FLAGS — MUST CONFIRM AT BUILD TIME (Aug 1)

**(a) Re-render "flicker" / image RE-DOWNLOAD — UNCONFIRMED.**
Whether re-minting causes a visible flicker or forces the closet grid to RE-DOWNLOAD every image (vs. reusing the already-cached bitmap) is not yet confirmed. It depends on which image component the closet grid uses and how it caches by URL. Because a re-minted signed URL is a NEW string (different token/expiry query params), a naive `<Image>` may treat it as a new source and re-fetch. This must be confirmed AT BUILD TIME on Aug 1 — check the exact `<Image>` component + caching behavior at `App.js:2138-2142`, and test on-device that the swap is smooth (ideally no visible re-download). If it re-downloads visibly, consider Option B (per-image `onError` self-heal) or a cache-friendly refresh instead.

**(b) Your Looks saved-outfit cards are NOT covered by this fix — OUT OF SCOPE.**
Already-generated outfit cards in Your Looks hold their OWN copies of item objects (with their own `photoUri`) captured at generation time. Re-minting `wardrobeItems` will NOT retroactively refresh those specific cards. This is out of scope for the reported Closet bug. Those cards get fresh URLs on the next Generate anyway. Flagging for awareness, not scoping in.
